## 3. Architecture Decisions

Three important architecture decisions were documented:

### Microservices Architecture

**Decision:** Use three independent services instead of a monolithic application.

**Alternative considered:** A single application containing all functionality.

**Reason:** Independent services provide clearer responsibility boundaries and allow individual components to evolve and scale separately.

Reference: ADR-001.

### HTTP and RabbitMQ Communication

**Decision:** Use synchronous HTTP communication for direct service requests and RabbitMQ for asynchronous event communication.

**Alternative considered:** Using synchronous HTTP for all communication.

**Reason:** HTTP is suitable for immediate request-response operations, while RabbitMQ will support asynchronous analytics event processing.

RabbitMQ integration is planned for a later development phase.

Reference: ADR-002.

### Database per Service

**Decision:** Each service will own its data and database responsibilities.

**Alternative considered:** A shared database accessed directly by all services.

**Reason:** Independent data ownership reduces coupling and prevents services from depending directly on another service's internal database structure.

Reference: ADR-003.

## 4. AI Assistance and Human Verification

AI assistance was used during architecture documentation and implementation planning.

One concrete AI error occurred while preparing the architecture diagram: an initial version showed the Redirect Service accessing the Link Service database directly.

This contradicted the database-per-service architecture decision.

The design was reviewed and corrected so that the Redirect Service communicates with the Link Service through its HTTP interface instead of accessing its database directly.

This demonstrated the importance of reviewing AI-generated technical suggestions against established architecture decisions.
